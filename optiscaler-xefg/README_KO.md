# JaeYun XeFG6x R4 — 2026-09-26

R3에서 확인한 자원 수명 결함을 보완하고 자체 버퍼·입력 누락 진단을 추가한 빌드입니다. R3 로그에서는 GPU 메모리 예산 초과가 관측됐지만, 제공된 CrashInfo에는 충돌 함수와 예외 코드가 없어 이번 실제 CTD 원인이 이 결함이라고 확정된 것은 아닙니다.

## 수정 내용

1. 화면 복사본 연결 보존
   이미 저장된 프레임 자원을 같은 함수에 다시 전달할 때 자체 복사본 포인터를 지우던 R3 결함을 수정합니다. 새로운 외부 입력과 내부 재전달을 구분해, 재전달에는 유효한 복사본과 자원 상태를 보존하고 새 입력에는 이전 프레임의 복사본이 잘못 붙지 않도록 합니다.

2. 자원 정리와 작업 등록 동시 접근 보완
   종료 시 신규 모드 작업을 차단하고 진행 중인 작업이 끝난 뒤 관련 GPU queue를 확인합니다. 명령 제출 전 queue 등록과 제출 완료 처리를 같은 작업 수명 안에서 수행합니다. 모드가 자원을 사용하는 명령을 기록했지만 아직 제출되지 않은 경우도 추적합니다. 완료를 입증할 수 없으면 해당 자원을 강제로 해제하지 않습니다.
   복사 버퍼·동기화 객체·보조 자원은 Intel context 및 관련 작업의 종료를 확인한 뒤 정리합니다. 매 프레임 GPU 전체 완료 대기나 강제 메모리 비우기를 추가하지 않습니다. 예외 상황의 자원 보존은 누수의 일반 해결책이 아니라 사용 중인 자원의 조기 해제를 막는 방어 처리입니다.

3. 자체 복사 버퍼 진단
   자체 복사 버퍼의 할당·반환·실패, 현재 및 최대 개수·크기와 내부 재전달의 복사본 보존을 기록합니다. 버퍼 크기는 모드가 추적하는 할당 크기이며, 게임 전체의 VRAM 사용량이나 실제 물리 상주량과 같지 않습니다. 기존 LongSession의 프로세스 DXGI 예산·사용량과 함께 원인을 구분하는 자료입니다.

4. 입력 누락 진단과 반복 경고 요약
   깊이·움직임 정보 중 어떤 입력이 준비되지 않았는지 구분하고 누락·회복 구간을 요약합니다. 프레임마다 동일 경고를 반복하는 양을 줄입니다. 관찰을 추가하는 변경이며 입력이 없는 프레임을 억지로 생성하지 않습니다.

## 유지 조건

- Intel XeFG 출력, 최대 6배(보간 5장 + 원본 1장) 제한 해제. 동봉 설정의 초기 선택은 이전 배포본과 같은 3배입니다.
- FFX 업스케일러, 업스케일 비율 1.5, FSR4 preset 1, 기존 약 152.7 FPS 제한.
- 기존 HDR·노출·색상·샤프닝 설정 및 R2의 화질·시간·이력 처리 보완.
- R3의 pacing 회복, 실패 시 자원 보존, descriptor 등록 및 LongSession 진단 기능.
- Intel/AMD 및 기타 구성 DLL은 R3와 동일합니다. 새로 빌드한 실행 파일은 dxgi.dll입니다.
- DLSS5/NR 또는 추가 프레임 생성 모드를 결합하지 않습니다. DLSSG 입력 이름은 게임에서 프레임 생성 정보를 받는 호환 경로이고 실제 출력은 Intel XeFG입니다. 기존 비활성 호환 DLL은 구성 보존을 위해 그대로 둡니다.

INI는 R3 배포본에서 LogFileName만 OptiScaler-JaeYun-R4.log로 바뀝니다. 로그는 dxgi.dll과 같은 폴더에 생성되며 재실행 전에 복사해 보관하십시오.

## 검증 범위와 한계

소스 해시, 실제 구현을 추출한 복사본 재전달·할당 실패 시험, 작업 수명 동시성 시험, 진단 카운터 시험, 기존 회귀 검증, Windows x64 Release 빌드, DLL export 및 PDB 일치와 최종 패키지 보존 검사를 수행합니다. 구체적인 결과는 TEST_RESULTS.json, BUILD.json, PACKAGE_AUDIT.json에 기록합니다.

실제 Cyberpunk 2077/RX 9070 XT에서 장시간 플레이·프레임·화질은 이 빌드 환경에서 검증하지 못했습니다. 게임 엔진과 드라이버가 소유한 자원을 임의로 해제하거나 VRAM을 RAM으로 강제 이전하지 않습니다. 전체 메모리 예산 초과나 이번 CTD의 완전한 해결을 보장하는 빌드는 아닙니다.

정리 시 작업 종료나 제출 취소를 확인할 수 없으면 자원을 보존하고 FG를 비활성 상태로 유지할 수 있습니다. 이 경우 로그에 구체적인 실패 이유를 남기며, 정상적인 전체 swapchain 재생성 또는 게임 재시작이 필요할 수 있습니다. 확인되지 않은 명령 폐기를 시간만으로 안전하다고 처리하지 않습니다.
